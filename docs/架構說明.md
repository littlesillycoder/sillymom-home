# 傻媽萬事通：架構說明

## 1. 原則

1. **模組化**：照業務功能分模組。每個模組有自己的畫面、商業規則、資料表和測試。
2. **模組之間只透過公開介面或事件溝通**，不讀別的模組的內部程式，也不直接讀寫別的模組的資料表。
3. **外部服務一律透過「替換介面」**：金流、發票、簡訊、通知不直接呼叫第三方程式，之後才能換服務（例如賣到歐洲改用 Stripe）。
4. **不寫死**：畫面文字放在語言檔；金額存「數字＋幣別代碼」；時間存 UTC，顯示時依地區時區轉換。
5. **資料庫只用標準 PostgreSQL 功能**，加上 Supabase 的登入和 Row Level Security。登入和檔案存取包在各自的模組裡，之後要搬到別的資料庫，只改這兩個模組。
6. **安全預設開啟**：每張表都有 Row Level Security；每個 issue 都要附權限測試。

## 2. 資料夾結構（建議）

```
src/
  app/                    # Next.js 路由，只放頁面組裝，不放商業規則
    [locale]/             # zh-TW、en
  modules/
    auth/                 # 帳號：註冊、手機驗證碼、登入、角色
    member/               # 會員：地址、緊急聯絡人、我信任的師傅、帳號設定
    technician/           # 師傅：申請、審核、個人頁、排班
    matching/             # 搜尋配對：師傅列表、篩選、推薦排序
    booking/              # 求助與預約：描述問題、預約、改期或取消
    video/                # 視訊：房間、錄影、計時
    diagnosis/            # 診斷與報價：診斷單、報價、加價同意

    billing/              # 帳務：平台費、退款、抵用金

    providers/            # 外部服務替換介面

```

## 3. 每個模組的結構

```
modules/<模組>/
  README.md        # 負責什麼、公開哪些介面、發出和接收哪些事件
  index.ts         # 公開介面：別的模組只能 import 這個檔案
  components/      # 這個模組的畫面元件
  server/          # 商業規則、資料存取（只能讀寫自己的資料表）
  events.ts        # 這個模組發出的事件型別
  tests/
```

自動檢查：用 ESLint 規則（例如 `eslint-plugin-boundaries` 或 `no-restricted-imports`）禁止 import 別的模組的內部檔案，只能 import `modules/<模組>/index.ts`。違反的話 CI 不通過。

## 4. 事件

模組之間的流程用事件串起來。例如：

| 事件 | 發出 | 接收 |
|---|---|---|
| `video.ended`（含通話秒數） | video | billing（滿 3 分鐘才收平台費）、review（開放評價）、messaging（通知） |
| `booking.cancelled` | booking | billing（逾時費、抵用金）、messaging |
| `homevisit.code_verified` | homevisit | billing（直接到府平台費）、messaging |
| `dispute.opened` | dispute | admin（申訴列表）、video（延長錄影保存）、messaging |
| `technician.approved` | technician | billing（上架審核費）、messaging |

第一版用資料庫的事件表加上同一個程式內的背景處理，不需要另外架訊息佇列。事件格式先定好，之後要拆服務時不用改模組。

### 4.1 資料表（`supabase/migrations/*_events.sql`）

| 資料表 | 內容 |
|---|---|
| `events` | 事件類型、發出模組、內容（只放編號）、時間、分派時間 |
| `event_deliveries` | 每個接收者一筆：狀態（pending、processing、done、failed）、嘗試次數、下次重試時間、錯誤訊息 |

### 4.2 流程

```
發出 ─┬─ 一般：emitEvent()（寫完業務資料後）
      └─ 同交易：資料庫函式裡呼叫 public.emit_event()
        ↓
 events（一筆）
        ↓ 分派 fan_out_events()：依 src/event-handlers.ts 的接收者清單
 event_deliveries（每個接收者一筆，同一事件同一接收者只會有一筆）
        ↓ 認領 claim_event_deliveries()：FOR UPDATE SKIP LOCKED，兩個程式不會拿到同一筆
 接收者處理 → 成功 done；失敗重試（1 分、5 分、30 分、2 小時、12 小時），共 6 次都失敗就 failed
```

- **什麼時候處理**：`emitEvent()` 發出後，在回應使用者之後立刻處理（Next.js `after()`）。沒處理到的，由補處理網址 `POST /internal/events/process` 接手（排程在部署時設定）。
- **兩種發出方式怎麼選**：跟錢、權限、後台操作紀錄、申訴有關的事件，一定要用同交易方式，避免「資料寫了、事件沒發」造成帳務對不起來或操作紀錄缺漏。其他（例如通知）可以用一般方式。
- **接收者**：在模組的 `index.ts` 公開 `defineHandler(...)`，加到 `src/event-handlers.ts`。必須寫成「執行兩次結果一樣」。

### 4.3 資安

- 事件表開啟 RLS、不建 policy、收回 anon／authenticated 權限；事件函式只有 `service_role` 能執行。
- 事件內容不能有個資：程式（`shared/events/pii.ts`）和資料庫（`events_validate` 觸發程序）都會擋下欄位名稱含 phone、address、email、name、token、card、id_number 等字的事件；內容最大 8KB。
- 資料庫的檢查**不用 check constraint**：check constraint 失敗時錯誤明細會附上整筆資料（`Failing row contains ...`），被擋下的個資會進錯誤訊息和 log。改用觸發程序自己丟錯誤，只寫規則和欄位名稱，不寫值。之後其他資料表若有可能含個資的欄位，也照這個做法。
- 錯誤訊息只存訊息文字，遮掉 Email 和長串數字，截短到 500 字，不存事件內容。
- 補處理網址：只接受 POST，要帶 `Authorization: Bearer <EVENTS_CRON_SECRET>`（至少 32 字元，比對防計時攻擊）；沒設定或錯誤一律 404；回應只有筆數。

### 4.4 已知限制

- 伺服器端都用同一把 secret key，資料庫本身不會阻止 A 模組讀寫 B 模組的資料表，目前靠 lint 和 code review（之後討論：#85）。
- 事件紀錄的保存天數要從平台設定讀，平台設定建好後再補自動清除。

## 5. 外部服務替換介面

```ts
// shared/providers/payment/types.ts（示意）
export interface PaymentProvider {
  bindCard(input: BindCardInput): Promise<CardToken>;
  charge(input: ChargeInput): Promise<ChargeResult>;
  refund(input: RefundInput): Promise<RefundResult>;
  getTransaction(id: string): Promise<Transaction>;
}
```

- 每個介面都有 `mock` 實作，開發、測試、投資人展示都用 mock。
- 用環境變數選擇實作，例如 `PAYMENT_PROVIDER=mock|ecpay`、`SMS_PROVIDER=mock|every8d`、`NOTIFY_PROVIDER=mock|line`。
- 程式其他地方只能透過介面呼叫。

## 7. 環境

| 環境 | 用途 | 外部服務 |
|---|---|---|
| 本機 | 開發 | 全部 mock；Supabase 連開發用雲端專案 `sillymom-home-dev`（不用裝 Docker） |
| 自動測試 | 每個 PR 在 GitHub Actions 跑 | 全部 mock；Supabase 用 `supabase start` 開暫時資料庫，不碰雲端資料 |
| 預覽 | 每個 PR 自動部署 | 全部 mock；LiveKit 免費版 |
| 展示 | 給投資人看 | 全部 mock；LiveKit 免費版；示範資料 |
| 正式 | 上線 | 真的服務 |

## 8. 測試

- 商業規則：單元測試（例如 Vitest）
- 權限：每張表都要有測試，證明 A 帳號讀不到 B 帳號的資料
- 主要流程：端對端測試（例如 Playwright），在 390 和 1440 寬度各跑一次
